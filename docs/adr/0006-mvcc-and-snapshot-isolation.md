# ADR 0006: Multi-Version Concurrency Control (MVCC) and Snapshot Isolation

## Status
Accepted

## Context
AegisDB requires high-throughput, concurrent read/write transactional capability beyond single-version locking (Master Plan §9 & §17 - Phase 6 / US011). In traditional 2-Phase Locking (2PL), readers acquire shared locks and writers acquire exclusive locks. Under high read/write contention, readers block writers and writers block readers, leading to lock convoying, high tail latency, and potential deadlocks.

To achieve superior scalability and predictable tail latency under concurrent workloads, AegisDB adopts **Multi-Version Concurrency Control (MVCC)** with **Snapshot Isolation (SI)**.

Key design requirements:
1. Lock-free read path: readers must never block writers, and writers must never block readers.
2. Snapshot Isolation: each transaction reads an immutable point-in-time snapshot of the database.
3. Strict visibility rules: dirty reads, uncommitted writes, and aborted transactions must be strictly invisible.
4. Read-Your-Own-Writes: an active transaction must see its own uncommitted modifications.
5. First-Committer-Wins: concurrent write conflicts (lost updates) must be detected and rejected.
6. Garbage Collection Safety: old versions no longer needed by any active snapshot must be reclaimed without deleting versions still needed by active readers.
7. Modularity & Zero Coupling: algorithmic MVCC core must not depend on Spring, gRPC, or management frameworks.

## Decision
1. **Lock-Free Singly-Linked Version Chains (`VersionChain`)**:
   - Each key is backed by a `VersionChain` holding immutable `VersionedValue` nodes ordered newest-to-oldest.
   - Appending new versions uses atomic Compare-And-Swap (`AtomicReference.compareAndSet`) on the chain head.
   - Readers traverse the singly-linked chain without acquiring any synchronized locks or read-write locks, ensuring linear read scalability across CPU cores.

2. **Monotonic Snapshot Timestamps (`TimestampProvider` & `Snapshot`)**:
   - Logical monotonically increasing timestamps are generated by `TimestampProvider`.
   - `Snapshot` captures `readTimestamp`, the reader transaction ID, and a point-in-time set of in-flight active transactions (`activeTxIds`).
   - Implements `AutoCloseable` to safely register and unregister with the active snapshot tracker for garbage collection watermarking.

3. **Deterministic Visibility Engine (`VisibilityRule`)**:
   - Pure, stateless visibility evaluation enforcing:
     1. Aborted versions are never visible.
     2. Own uncommitted writes are visible to the writing transaction (Read-Your-Own-Writes).
     3. Uncommitted versions from other transactions are invisible (Dirty Read Prevention).
     4. Versions from transactions active at snapshot establishment are invisible.
     5. Future committed versions (`commitTimestamp > snapshot.readTimestamp`) are invisible.
     6. Committed versions at or before snapshot timestamp are visible.

4. **First-Committer-Wins Write Conflict Detection**:
   - When a transaction modifies a key, `MvccStore` validates:
     - The key is not locked by another uncommitted transaction.
     - The latest committed version of the key was not committed after the transaction's start timestamp.
   - Any violation immediately throws `WriteConflictException`, preventing lost updates.

5. **Watermarked Garbage Collection (`MvccGarbageCollector`)**:
   - Pruning watermark is established as `watermark = minActiveSnapshotTimestamp()`.
   - Versions committed after the watermark are retained.
   - The single newest committed version at or before the watermark is retained as the baseline.
   - Obsolete historical versions strictly older than the baseline are pruned.
   - Obsolete tombstone keys (deleted records with no remaining versions) are completely removed from the store.

6. **Raft State Machine Snapshot Integration**:
   - `MvccStore` serializes all active committed key-value records into a framed binary snapshot with CRC32 checksums (`0x4D564343` magic header), fully compatible with Raft log compaction.

## Consequences
### Positive
- **Extreme Concurrent Read Throughput**: Lock-free reads guarantee zero lock contention and zero wait-time for readers.
- **Repeatable Reads & Anomaly Prevention**: Snapshot Isolation completely eliminates Dirty Reads, Lost Updates, and Non-Repeatable Reads.
- **Bounded Memory Footprint**: Background/on-demand GC continuously reclaims obsolete version nodes and tombstone keys.
- **Strict Architectural Independence**: `aegisdb_mvcc` module has 0 dependencies on Spring, gRPC, or management libraries, proven by automated ArchUnit tests.

### Negative
- Multi-version chains consume additional heap memory until garbage collection reclaims obsolete historical nodes.
- Under pure Snapshot Isolation, transactions modifying disjoint keys based on overlapping reads may experience write skew (to be augmented with serializable conflict validation in Phase 7).
